Conversations & Expressions in Digital.ai Agility

When conversations were released years ago when I was a platform engineer at VersionOne, I didn't quite understand the witchcraft until I got some insight from one of my teammates Rajiv Delwadia, one of the co-founders. Since then, I struggled to remember how to navigate conversations because I never documented it. Well, not quite since I did a StackOverflow response on it back in 2014 but it still doesn't seem to stick so I took sometime last year to walk through it. Without further ado...

A conversation is a container. Every comment you post is an expression inside it. This page shows how the pieces point at each other, what changes in the data each time someone comments on a story, and how to do every step through /api/asset with JSON (I still say JaySAWN).

How it works

A walk through one security review on story S-01234. Each step lists what the person does; the next section shows exactly which attributes change.

  1. Jim comments on the story.This component needs to be checked for SSRFThis creates the conversation and its first expression. Through the API you create both in a single request, linked by an alias.
  2. Look at the story again.You now have a conversation. The story points at Jim's expression, and that expression points at the new conversation.
  3. Mark replies.I actually ran it through Semgrep and it didn't detect anythingA second expression joins the same conversation and Mark becomes a participant. The story doesn't change.
  4. Jim replies and references a defect.Default rules don't follow our HttpFetcher wrapper. Logged D-02001 to add a custom rule.A third expression. This one mentions a defect, so the defect now links back to the conversation.
  5. Mark replies and pulls in a reviewer.Custom rule flagged fetchPreview(). Fix is pushed. @Linda, can you review?A fourth expression. Mentioning Linda adds her as a participant even though she hasn't written anything.
  6. Read the whole thread back.One query from the story, or one from the conversation, returns everything above in order.

Doing it through /api/asset with JSON

Every step is one POST to /api/asset with Content-Type: application/json. The same endpoint creates ("AssetType"), updates ("from" + "update"), and reads ("from" + "select"). The // lines in the samples are notes for you — strip them before sending, since JSON has no comments.

Request template — save each payload as a .json file
curl -X POST "https://<host>/<instance>/api/asset" \
  -H "Authorization: Bearer $V1_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  --data-binary @step1.json

# Dry run first: nothing is written, you see what would change
curl -X POST "https://<host>/<instance>/api/asset?previewOnly=true" ...

1Create the conversation and its first expression

step1.json — conversation first, then the expression that uses its alias
[
  {
    "@conv": {
      "AssetType": "Conversation"
    }
  },
  {
    "AssetType": "Expression",
    "Content": "This component needs to be checked for SSRF",
    "BelongsTo": "@conv",
    "Mentions": ["Story:1100"]
  }
]
Response (trimmed)
{
  "complete": true,
  "assetsCreated": {
    "oidTokens": [
      "Conversation:3000",
      "Expression:3001"
    ],
    "count": 2
  },
  "commandFailures": { "commands": [], "count": 0 }
}
// Keep Conversation:3000 — every reply needs it.
Through the API, the conversation comes first

An expression needs a conversation to belong to, so step 1 creates both in one request. The first command creates the conversation and names it @conv. The second command creates the expression and sets BelongsTo to "@conv", which the server swaps for the real OID. The order matters: the alias has to be defined before anything refers to it.

An alias only exists inside the request that defines it. You only need it this once. Every reply after this uses the real OID from the response, Conversation:3000.

2Observe: find the conversation from the story

step2.json
{

  "where": { "Number": "S-01234" },
  "select": [
    "Name",

      "from": "MentionedInExpressions",
      "select": [
        "Content",
        "Author.Name",
        "BelongsTo",
        "BelongsTo.Participants.Name"

    }

}

3Reply in the same conversation

step3.json
{
  "AssetType": "Expression",
  "Content": "I actually ran it through Semgrep and it didn't detect anything",
  "Author": "Member:1005",
  "BelongsTo": "Conversation:3000",
  "InReplyTo": "Expression:3001"
}
// BelongsTo joins the existing conversation;
// InReplyTo sets the threading.
Response (trimmed)
{
  "assetsCreated": {
    "oidTokens": ["Expression:3002"],
    "count": 1
  }
}
// Participants and LatestActivityAt on
// Conversation:3000 are updated by server rules,
// not by anything in this payload.
No alias needed from here on

The conversation already exists, so replies point BelongsTo straight at Conversation:3000. InReplyTo only sets the threading; it doesn't put the reply in a conversation. Send both.

{
  "from": "Conversation",
  "where": { "ID": "Conversation:3000" },
  "select": [
    "Participants.Name",
    "ContainedExpressions.Author.Name"
  ]
}
// Participants: Jo, Mark, Linda
// Authors:      Jo, Mark  (Linda wrote nothing)

6Read the whole thread in order

From the conversation
{
  "from": "Conversation",
  "where": { "ID": "Conversation:3000" },
  "select": [
    "Topic.Content",
    "Participants.Name",
    "LatestActivityAt",
    {
      "from": "ContainedExpressions",
      "select": [
        "Content",
        "Author.Name",
        "AuthoredAt",
        "InReplyTo",
        "Mentions.Name"
      ],
      "sort": ["+AuthoredAt"]
    }
  ]
}
From the story, every conversation it's in
{
  "from": "Story",
  "where": { "Number": "S-01234" },
  "select": [
    "Name",
    {
      "from": "MentionedInExpressions.BelongsTo",
      "select": [
        "Topic.Content",
        "ContainedExpressions.@Count",
        "Participants.Name"

    }

Verify these before relying on them

The request shapes (create with AssetType, query with from/where/select, nested sub-selects, a JSON array for multiple commands, previewOnly) follow the documented /api/asset behavior. The Expression-specific parts weren't run against a live instance: whether Author is writable or always set from your token, whether a sub-select from accepts a two-hop path like MentionedInExpressions.BelongsTo, whether sort works inside a sub-select, and whether the UI also adds the story to a reply's Mentions. Run each with ?previewOnly=true first, and check failures in commandFailures.
